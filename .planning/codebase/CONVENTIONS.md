# Coding Conventions

**Analysis Date:** 2026-07-30

Conventions below are inferred from the code itself and cross-checked against `CLAUDE.md`. Where `CLAUDE.md` and the code disagree, the code is documented as the source of truth and the discrepancy is flagged.

## Naming Patterns

**Files:**
- **React components** — `PascalCase.tsx`, one component per file. `src/components/agency/ChatInterface.tsx`, `src/components/agency/MediaUploader.tsx`, `src/components/agency/BrandProfileForm.tsx`.
- **shadcn/base-ui primitives** — `kebab-case.tsx` in `src/components/ui/`. `src/components/ui/dropdown-menu.tsx`, `src/components/ui/scroll-area.tsx`. Do not rename these; they are generated by the `shadcn` CLI.
- **Library modules** — `kebab-case.ts`. `src/lib/agents/intent-router.ts`, `src/lib/mixpost/brand-mapping.ts`, `src/lib/media/process-pipeline.ts`.
- **Agent tools** — `kebab-case.ts` matching the tool's snake_case name. The `scan_website` tool lives in `src/lib/agents/tools/scan-website.ts`; `write_email_campaign` in `src/lib/agents/tools/write-email-campaign.ts`.
- **Tests** — co-located `<module>.test.ts` beside the module under test. `src/lib/mixpost/brand-mapping.test.ts` sits next to `src/lib/mixpost/brand-mapping.ts`. See `TESTING.md`.
- **Routes** — Next.js App Router conventions: `page.tsx`, `route.ts`, `layout.tsx`, dynamic segments as `[brandId]`, `[conversationId]`, `[brandSlug]`.
- **Scripts** — `kebab-case.ts` (typed, run with `tsx`) or `kebab-case.mjs` (throwaway/admin, run with `node`) in `scripts/`.

**Functions:**
- `camelCase` throughout.
- **Tool factories are `create<ToolName>Tool`** — `createScanWebsiteTool`, `createSaveOutputTool`, `createPublishToSocialTool` (`src/lib/agents/tools/index.ts:3-52`).
- **Reusable tool logic is `<toolName>Core`** — see the `*Core` section below.
- Predicates read as sentences: `isWebsiteScanRequest`, `canAccessBrand`.
- Assertions throw: `assertProjectScope` (`src/lib/security/execution-scope.ts`).

**Variables:**
- `camelCase` for locals and props; `SCREAMING_SNAKE_CASE` for module constants (`HIDDEN_FROM_MCP` in `src/lib/mcp/server.ts`, `PLATFORM_CHAR_LIMITS` in `src/lib/post-versions.ts`).
- Database column names stay `snake_case` in the object literals passed to Supabase (`user_id`, `brand_id`, `cost_cents`) — never camelCase them at the query boundary; PostgREST rejects unknown keys.

**Types:**
- `PascalCase` interfaces and type aliases, all shared shapes centralised in `src/types/database.ts` (935 lines): `AgentType`, `Brand`, `AgentConfig`, `Task`, `Goal`, `MediaItem`.
- Zod schemas are `PascalCase` + `Schema` suffix: `CreateOutputSchema` (`src/app/api/outputs/route.ts:36`).

## The `*Core` Pattern (mandatory for reusable tool logic)

**A tool's real logic is exported as a plain async function separate from its AI-SDK `tool()` wrapper.** The wrapper is a thin `execute` shim. This is what lets HTTP routes, scripts, cron jobs and other tools reuse the logic without going through an LLM.

Existing `*Core` functions:

| Function | File |
|---|---|
| `scanWebsiteCore` | `src/lib/agents/tools/scan-website.ts:61` |
| `scanSocialCore` | `src/lib/agents/tools/scan-social.ts:37` |
| `scanGithubCore` | `src/lib/agents/tools/scan-github.ts:28` |
| `extractBrandKitCore` | `src/lib/agents/tools/extract-brand-kit.ts:275` |
| `researchIndustryCore` | `src/lib/agents/tools/research-industry.ts:39` |

The shape, from `src/lib/agents/tools/scan-website.ts`:

```ts
/**
 * Core rendered scan logic. Every NRS entry point uses this single evidence
 * source; callers receive facts and explicit unknowns, never a raw HTML guess.
 */
export async function scanWebsiteCore(
  supabase: SupabaseClient,
  userId: string,
  brandId: string,
  url: string,
  focus?: string,
  traceId?: string,
) { /* … persists project_scans + logAudit, returns results … */ }

export function createScanWebsiteTool(supabase: SupabaseClient, userId: string, brandId: string) {
  return tool({
    description: '…',
    inputSchema: z.object({ url: z.string().url(), focus: z.enum([...]).optional() }),
    execute: async ({ url, focus }) => scanWebsiteCore(supabase, userId, brandId, url, focus),
  })
}
```

Signature convention: `(supabase, userId, brandId, ...toolArgs)` — positional, Supabase client first, never a context object.

Non-agent consumers proving the pattern earns its keep:
- `src/app/api/brands/[brandId]/review/route.ts:36,44,55` — the one-click brand review calls all three scan cores in parallel.
- `src/app/api/admin/backfill-research/route.ts:71` — `researchIndustryCore`.
- `src/lib/discovery/project-discovery-run.ts:99,121` — discovery pipeline.
- `src/lib/mcp/director-job.ts:173` — the Director grounds a Telegram reply on a real scan before writing.
- `src/lib/agents/tools/deep-competitor-scan.ts:229` — one tool reusing another tool's core.
- `scripts/setup-projects.ts:512,521,532` — CLI provisioning.

**When adding a tool:** if any non-agent caller could plausibly need the logic (a route, a script, a cron, another tool), export `<name>Core` first and make `execute` a one-liner delegating to it. If the tool is genuinely agent-only (e.g. `word_count`), an inline `execute` is fine.

## Tool Factory Pattern

All 62 files in `src/lib/agents/tools/` follow the same shape:

1. `import { tool } from 'ai'` and `import { z } from 'zod/v3'`.
2. Export one or more `create*Tool(...)` factories that close over `(supabase, userId, brandId, …)`.
3. Return `tool({ description, inputSchema, execute })`. `description` is written for the model, in full sentences, saying *when* to use the tool — not just what it does.
4. Register the factory in `src/lib/agents/tools/index.ts`, then add the tool to the per-agent-type set inside `getToolsForAgent(agentType, ctx)`.

`ToolContext` (`src/lib/agents/tools/index.ts:54-62`) is the only context object:

```ts
export interface ToolContext {
  supabase: SupabaseClient
  userId: string
  brandId: string
  conversationId: string | null
  agentRegistryId?: string | null
  /** Present for autonomous heartbeat work; approval requests retain this link. */
  taskId?: string | null
}
```

A file may export several factories when they share a client (`src/lib/agents/tools/canva.ts` exports 28; `src/lib/agents/tools/proforma.ts` exports `createReadProformaTool` + `createUpdateProformaTool`).

**MCP exposure is a deliberate decision per tool.** After registering a tool, decide whether it belongs on the MCP surface. Multi-step, content-writing or orchestration tools must be added to `HIDDEN_FROM_MCP` in `src/lib/mcp/server.ts` so plug-in AI clients are forced through `chat_with_director`. Query-only and bounded single-shot tools are auto-exposed by `adaptToolsForMCP` (`src/lib/mcp/tool-adapter.ts`).

## Zod: `zod/v3` for AI SDK schemas

`zod@^4.3.6` is installed, but **AI SDK tool schemas and API-route validation import from `zod/v3`** — 79 of the 80 zod imports in `src/` use `import { z } from 'zod/v3'`. The AI SDK's JSON-schema conversion and `src/lib/mcp/tool-adapter.ts` (which reads `zodSchema.shape` directly, `tool-adapter.ts:27-28`) rely on the v3 object internals.

The single exception is `src/app/api/stripe/checkout/route.ts:2` (`import { z } from 'zod'`), which never touches the tool adapter. **Default to `zod/v3`** unless you have a specific reason and no AI-SDK/MCP code path.

## The Three Supabase Clients

Never mix them. Pick by who is acting.

| Client | Factory | Use when | Files using it |
|---|---|---|---|
| `src/lib/supabase/server.ts` | `await createClient()` | Server components and API routes acting **as the signed-in user**. RLS applies. This is the default. | 89 |
| `src/lib/supabase/admin.ts` | `createAdminClient()` | Service-role work with **no user session**: webhooks, cron/heartbeat, MCP job workers, scripts. RLS bypassed — you must scope every query by `user_id`/`brand_id` yourself. | 45 |
| `src/lib/supabase/client.ts` | `createClient()` | Browser/`'use client'` components only. | 16 |

`src/lib/supabase/middleware.ts` `updateSession()` is a fourth, single-purpose client used only by `src/middleware.ts` to refresh the auth cookie on every request.

Rule of thumb: if the code path can be reached by an unauthenticated HTTP call (a webhook, a cron), use admin **and** scope manually. If a user is present, use server and let RLS do the work.

## Code Style

**Formatting** — no Prettier config in the repo; style is enforced by convention and consistency:
- **No semicolons.** `src/lib/agents/tools/scan-website.ts` has zero lines ending in `;`.
- **Single quotes** — 1,212 single-quoted imports vs 9 double-quoted.
- 2-space indent, trailing commas in multi-line literals.

**Linting** — `eslint.config.mjs`, flat config v9, extends `next/core-web-vitals` plus the `@typescript-eslint` plugin. Ignores `.next/**`, `node_modules/**`, `coverage/**`. `npm run lint` currently reports **0 errors, 39 warnings** — all warnings are `Unused eslint-disable directive` (stale `no-explicit-any` suppressions in `src/lib/mcp/server.ts`, `src/lib/mcp/tool-adapter.ts`, `src/lib/memory/store.ts`, `src/lib/webhooks/dispatcher.ts`, `src/lib/telegram/telegram-thread.ts`, `src/lib/content-optimisation/bandit.ts`). 23 are auto-fixable with `--fix`. **Zero errors is the bar for a change.**

**TypeScript** — `strict: true`, `noEmit`, `moduleResolution: bundler`, `allowImportingTsExtensions: true` (this is what lets tests import `./module.ts` with the extension — see `TESTING.md`). Path alias `@/*` → `./src/*`.

## Import Organisation

Observed order (no lint rule enforces it — follow it by hand):

1. Framework/runtime — `next/server`, `node:fs`, `node:assert/strict`
2. Third-party — `ai`, `zod/v3`, `@supabase/supabase-js`
3. Absolute internal via `@/` — `@/lib/supabase/server`, `@/types/database`
4. Relative — `./rendered-website-scan`

`import type { … }` is used for type-only imports (`import type { SupabaseClient } from '@supabase/supabase-js'`) — required by `isolatedModules`.

## Error Handling

**API routes** return `NextResponse.json` with an explicit status; they do not throw. Canonical shape (`src/app/api/outputs/route.ts`):

```ts
const { data: { user } } = await supabase.auth.getUser()
if (!user) return NextResponse.json({ error: 'Unauthorised' }, { status: 401 })

const parsed = CreateOutputSchema.safeParse(body)
if (!parsed.success) {
  return NextResponse.json({ error: 'Invalid request', details: parsed.error.issues }, { status: 400 })
}

const { data, error } = await query
if (error) return NextResponse.json({ error: error.message }, { status: 500 })
```

Order is always: auth check → input validation (`safeParse`, never `parse`) → query → error branch → success. Note the Australian spelling in `'Unauthorised'`.

**Agent tools never throw at the model.** A failure returns a plain object the model can read and act on:

```ts
return { error: 'Could not fetch brand. Please ensure the brand exists.' }
```

(`src/lib/agents/tools/extract-brand-kit.ts:292`, `src/lib/agents/tools/analyse-voice.ts:56`, `src/lib/agents/tools/get-brand-kit.ts:83`). Error strings are written **for the model**, telling it the recovery move — `'Could not read that project. Call list_projects for the ids you can access.'` About half the tool files (30 of 62) wrap their body in `try/catch` and convert the throw into this shape.

**Side-effect helpers swallow their own errors.** `logAudit` (`src/lib/agents/audit.ts:17-42`) is documented "Non-blocking — errors are logged but don't throw." Audit/telemetry failures must never break the user-facing path.

## Logging

No logging framework — `console.*` with a **bracketed module tag** as the first token:

```ts
console.error('[audit] Log failed:', error.message)
console.error('[mixpost] …')
console.warn('[user-webhooks] …')
```

Tags in use include `[mixpost]` (38), `[canva]`, `[heartbeat]`, `[goal-loop]`, `[chat]`, `[director-job]`, `[prompt-builder]`, `[registry]`, `[analytics]`. Use `console.error` for failures, `console.warn` for degraded-but-continuing, `console.log` sparingly. Never log PHI, API keys, or full request bodies.

**Client-side diagnostics do not use the browser console alone.** Per the non-technical-user principle, instrument the client to POST breadcrumbs to a server endpoint and read them from the terminal — see `src/components/agency/MediaUploader.tsx`, `src/app/api/debug/upload-log/route.ts`, `scripts/read-upload-trace.mjs`. Never ask the user to open DevTools.

## Function & Module Design

**Exports:** named exports only. `src/lib` has exactly one `export default` across 240 files. React pages/layouts use `export default` because Next.js requires it.

**Barrel files:** one real barrel — `src/lib/agents/tools/index.ts` — and it is a *composition* point (`getToolsForAgent`), not a re-export dump. Do not add pass-through `index.ts` files elsewhere; import modules directly.

**Parameters:** positional for `*Core` functions and tool factories (`supabase, userId, brandId, …`); a single typed object for anything with 4+ heterogeneous or optional fields (`logAudit({ … })`, `createCreateTaskTool({ … })`, `runMediaProcessingPipeline({ … })`).

**Return values:** discriminate on shape rather than throwing — `if ('error' in rendered)` (`src/lib/agents/tools/scan-website.ts:70`).

## UI Conventions

- **base-ui composition uses the `render` prop, never `asChild`.** 19 uses of `render={…}` in `src/`, **zero** uses of `asChild`. `@base-ui/react@^1.3.0`.
- **Colours are oklch only.** `src/app/globals.css` has 62 `oklch(` declarations and **zero** hex colours. Inline styles follow suit: `style={{ color: 'oklch(0.8 0 0)' }}` (`src/app/privacy/page.tsx`). Silver/chrome palette, hue ~240. The CSS property name `color` stays US-spelled (it's CSS); user-facing copy and identifiers use `colour` (`src/components/agency/BrandColoursEditor.tsx`).
- **`export const dynamic = 'force-dynamic'`** on pages rendering base-ui components — 71 files declare it.
- Fonts: IBM Plex Sans + Mono via `@fontsource`. Icons: `lucide-react`.
- Class merging: `clsx` + `tailwind-merge`; variants via `class-variance-authority`.
- **Never touch** `src/app/page.tsx` / `src/components/landing/WaterRippleHero.tsx`.

## Australian English

User-facing copy, comments and NRS-owned identifiers use Australian spelling: `colour` (609), `analyse` (139), `optimise` (36), `behaviour` (22), `organisation` (17). API error strings follow it too (`'Unauthorised'`). Tool names follow it (`analyse_voice`, `analyse_content_gaps`, `src/lib/content-optimisation/`).

The US spellings that remain are **not** violations — they are CSS properties (`color:`), DOM/library APIs, and third-party field names. Do not "fix" those.

## Money & Audit

- **All money is integer cents.** Columns and fields are `*_cents`: `budget_monthly_cents`, `spent_monthly_cents` (`src/lib/agents/registry.ts:40,78-111`), `cost_cents` (`src/lib/agents/audit.ts:38`), `budget_charge_cents` (`src/lib/mcp/director-job.ts:628`). No floats anywhere in a money path. Cost formula: `(inputTokens * 0.3 + outputTokens * 1.5) / 100` → cents.
- **`audit_log` is append-only.** Write through `logAudit()` (`src/lib/agents/audit.ts`) only — insert, never `UPDATE`/`DELETE`. There are no update/delete RLS policies on the table. Every meaningful action logs `{ userId, action, entityType, entityId, detail, costCents }`.

## Database

- Migrations live in `supabase/migrations/` (41 files, `NNN_description.sql`).
- The `updated_at` trigger function is **`update_updated_at()`** — confirmed at `supabase/migrations/001_initial_schema.sql:196` — not `update_updated_at_column()`.
- `src/types/database.ts` is the single source of truth for row shapes. **Read it before writing an update object** — Supabase/PostgREST rejects the *entire* update if it contains one unknown column and fails silently at the app layer. `media_items` has `transcription_status` but no `status` column; sending `status:` drops the whole write (PGRST204).
