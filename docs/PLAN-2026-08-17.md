# THE PLAN

**NotRealSmart — from a tool that works for one person to a product a stranger can buy and keep.**
Written 17 August 2026. Every fact below was checked against the running code or the live database; anything unverified is marked as such.

---

## 1. What we are building

We are building the four things that no publishing tool sells — a dated AHPRA/TGA compliance register a clinic can hand to a regulator, a no-login approval link a practice manager opens on a phone, a technical site audit we are already paying Google for weekly and currently deleting, and a working checkout — and we are building them on top of a composer that has stopped lying about what it publishes. Publishing itself is a commodity: Justin already self-hosts Mixpost for free and Zernio rents the same thing, so we stop chasing composer parity and start selling the evidence layer that sits either side of it.

---

## 2. The order, and why that order

**The bet:** a stranger renews in month two because of the register, the approval link and the site report — not because the composer has more buttons than Buffer. So we build the moat. But a moat with no gate is a hobby, so billing lands in the middle, not last.

**The order is forced by three dependencies, not by preference:**

1. **Security first, because Phase 4 opens a public door.** Four `/api/zernio/*` routes today call `createAdminClient()` and read `brandId` straight from the query string with zero authentication (verified: `connect`, `accounts`, `analytics` have 2 admin-client calls and 0 `getUser` calls each; `complete` has neither). Adding the first genuinely public unauthenticated route (`/review/[token]`) on top of that is compounding, not adding. The correct pattern already exists one directory over in `zernio/ads/route.ts`, which authenticates and has a `profileIdForOwnedBrand` helper. This is copying, not designing.
2. **The composer's honesty before the register.** A compliance register records what was published. If the composer discards the caption the user typed, the register faithfully records the wrong thing. Verified: `versions` appears at PostCreator.tsx lines 34, 90, 312, 726, 788 — state, updater, and two render props — and **nowhere in `handleSave`**. Same in PostComposerRoom.tsx.
3. **The register before billing.** Billing is roughly four days of wiring competent code that nothing currently calls. It is not the hard part and it is not the reason anyone stays.

**Deliberately later:** brand-aware theming, the public REST API, per-account caption variants, the Zernio inbox repair, ads campaign management, and AI cost attribution. Section 4 says when each comes back.

### House rules for this plan (apply to every phase; not repeated below)

- **Red then green.** Any test claimed as a regression guard must be shown *failing* before the fix and *passing* after, with both outputs pasted into the commit message. A test that was never red proves nothing.
- **State today's value next to the expected one.** "Returns 1" is unfalsifiable. "Returns 1; returns 0 across all 1,734 rows today" is not.
- **Delete dead controls, do not hide them.** A greyed-out control is a smaller lie, not the absence of one. Deleting forces re-justification; hiding comes back.
- **Predict the defect before you look for it.** Where a verification can name the specific thing it will find, it must.
- Australian English. `oklch` in authored CSS. Zod from `zod/v3` in tool schemas. `userSafeError()` for anything a tool returns — those strings are read aloud.

**Baseline, measured today:** `npm test` → `# pass 1000 / # fail 0`, 26.0 seconds. Every phase must leave this green.

### Phase 6 — Google Search Console, gated on a pre-flight
**Pre-flight ~1 day. The build is not scheduled until the pre-flight passes.**

GSC is the only source of the actual words people type, and nothing else in NRS has it. There is no Search Console code anywhere in the repo. It is last because two unknowns can silently destroy it.

**The pre-flight is the deliverable. Nothing else in this phase starts until it passes.**
1. Read off the Google Cloud Console and write down: **is the NRS OAuth consent screen in Testing?** If so, every subscriber's refresh token expires in **7 days** and the connection dies weekly while still reading as "connected". And **is `webmasters.readonly` marked sensitive** on that screen? If so, public release needs Google review (up to 10 days), a demo video, a privacy policy and brand verification. Neither is answerable from Google's public docs.
2. Test the OAuth-free path against one real property: add an NRS service-account email as a GSC **Full user** on `downscale.com.au` and call `searchAnalytics/query`. Google's help doc says a Full user can query performance, inspect URLs and submit sitemaps — but Google does **not** document service accounts for GSC and the same doc says an email group cannot be added. **This is unverified and must be tested before it appears in a design.** If it works, the consent screen problem disappears entirely.
3. **The gate:** a throwaway script prints ten real query rows with impressions and clicks for `downscale.com.au`. If it prints nothing, the property string or the auth is wrong and **no page gets built**.

**Then, and only then:** read-only scope for v1 (`sites`, `searchAnalytics/query`, `urlInspection/index:inspect` all fit under `webmasters.readonly`). Sitemap submission needs the write scope and is a separate, later, opt-in connect — never on a non-technical subscriber's first consent screen. Property selection uses the canonical host resolved in Phase 5 and prefers an `sc-domain:` property. Onboarding must survive "I don't have Search Console": try ANALYTICS/TAG_MANAGER verification first (Downscale already loads a `googletagmanager.com/gtag/js?id=AW-18254953551` tag — though note `AW-` is a Google Ads tag, not GA4, so edit access still needs confirming). Feed results into the Phase 5 Site Health panel with a visible "data is 2-3 days behind" note. **Do not print a data-retention figure anywhere** — the commonly-cited 16 months could not be found in Google's own docs and is unverified.

## 4. What is deliberately NOT in this plan

| Not doing | Why, and when it comes back |
|---|---|
| **Brand-aware theming** | 24 of 31 colour tokens in `:root` are chroma zero and the app is grey for every brand. Real work, but it is polish beside an evidence ledger, and a token swap only reaches ~80% of the colour surface — 914 hardcoded palette utilities across 137 classes stay generic regardless. The data-loss half is done in Phase 0. Comes back after Phase 5. Two traps to carry forward: never set a semantic token as an inline style on `<html>` (inline beats the `.dark {}` class rule on the same element and kills dark mode app-wide), and emit on the document root, not a wrapper (dropdowns, dialogs, sheets and tooltips all portal to `document.body`). |
| **Public REST API** | Thin when we want it — `resolveApiKey` and `assertProjectCapability` exist and `/api/calendar/feed` already proves the pattern outside MCP. ## 5. The risks that could sink this

1. **Phase 1 is a week and I have called it a week.** It contains six separable fixes. If it slips, the register slips, because a register of discarded captions is worse than none. The mitigation is the contract test: once it is green, the fix cannot silently regress.
2. **Mixpost's accepted option keys are unverified beyond instagram/facebook/tiktok/youtube.** Mixpost silently discards unrecognised keys. If reading the provider classes on the VPS proves harder than expected, Phase 1's option work shrinks to those four and everything else is deleted from the UI. That is an acceptable outcome; guessing is not.
3. **Moving the signature before the compliance gate changes what the model reviews.** It will now see signature text. That is correct — a signature containing a therapeutic claim should be caught — but it may block posts that used to pass. Expect one round of surprises on Downscale and treat them as findings, not bugs.
4. **"A dated register you can hand to AHPRA" is close to selling regulatory assurance.** That is a flag-to-a-real-lawyer decision, not an engineering one, and it must be settled before the phrase appears in any customer-facing copy. The engineering artefact is neutral; the sales claim is not.
5. **`/review/[token]` is a public unauthenticated route reading through the admin client.** Phase 0 is a hard prerequisite, not a nicety. If Phase 0 slips, Phase 4 slips with it.
6. **`publish-gate.test.ts` calls `checkPublishAllowed` with plain objects and no database.** If the ledger writer is not injected, those tests break and the temptation will be to weaken them. Inject the writer.
7. **Splitting `direct:read` off `direct:utility` breaks `mcp-scope-wiring.test.ts:26`** — verified, the literal string is pinned. Do not do it casually in Phase 0; it belongs with the REST API work.
8. **Two production tables have RLS disabled and this plan does not fix them.** `oauth_clients` (24 rows) and `oauth_auth_codes` (17 rows), exposed to anon. Enabling RLS without policies breaks MCP sign-in. Flagged, not touched, awaiting your call.
9. **The GSC consent-screen status and the service-account path are both genuinely unknown.** If the consent screen is in Testing, every subscriber connection dies after 7 days while reporting as connected — the exact silent-false-success failure mode. Phase 6 is gated on answering this, and if the answer is bad, Phase 6 becomes a longer project than it looks.
10. **The site audit reads 5 pages chosen by homepage link order.** On a 96-URL site that is a sample, not a crawl, and the UI must say so. Structured-data findings are shallower than they sound too: the scan captures only the JSON-LD `@type`, so we can truthfully say "no LocalBusiness on any page we read" but cannot say whether an existing one is correct.
11. **Changing `pagespeed.ts` touches a live weekly cron that already messages you.** Extend `report.test.ts` before touching `measure()`, not after.
